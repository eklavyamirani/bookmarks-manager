Keep the knowledge graph inside Postgres

Issue #15 asks whether bookmarks should move to Apache AGE or a separate Neo4j/Memgraph store. The proposal: neither. Use plain tables with an edge table, recursive SQL, and pgvector later. The benchmark below shows plain SQL is fast enough at the 10k-bookmark target.

The save flow

Saving is instant, enrichment runs after

QueueA Postgres table with FOR UPDATE SKIP LOCKED, run by a background worker in the API process. No Redis or RabbitMQ.
FailureA failed fetch leaves the bookmark usable with status failed. Re-running enrichment means queueing the job again.
SSRF guardThe fetcher refuses private, loopback and link-local addresses, including after redirects, because MCP clients can add any URL.
No LLM in P1Topics and embeddings are P2, behind an OpenAI-compatible endpoint. The provider is picked in ADR 0002.
Found along the way

Things that need action

Breaks on upgrade

Postgres 18 moved its data directory

Compose still uses 18beta1. On 18 GA images the data lives in /var/lib/postgresql/18/docker, so the current mount misses it.

- postgres-data:/var/lib/postgresql/data
+ postgres-data:/var/lib/postgresql
Design rule

Reading queue must cap its seeds

Seeding from all 486 reads in 7 days: 285 ms p50. Seeding from the 30 most recent: 22 ms. Cap it and weight by recency.

Design rule

Path search detours through hubs

Bookmark 42 to bookmark 2599 came back as 42 → tag 20001 → 2599: correct, but useless. FR-C3 needs a penalty for highly connected nodes.

Breaks NFR-3

Devcontainer doesn't match the app

The base image ships .NET 8 but the backend targets net9.0. The nvim download is hard-coded to arm64, so the build fails on amd64.
